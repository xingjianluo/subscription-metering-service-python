# 订阅计量与结算服务：规则、幂等边界与验证方式

本服务用本地存储（内存 + 原子写 JSON 文件）和模拟支付网关，打通
**用量上报 → 窗口聚合 → 出账 → 结算 → 重放校验** 整条链路，不接真实支付渠道。

- 金额：`Decimal`，单位元，每行金额按 `ROUND_HALF_UP` 四舍五入到分（0.01）。
- 时间：左闭右开区间 `[start, end)`；服务内部使用无时区 UTC 时间。

---

## 1. 套餐（Plan）

字段：`base_price`（整月基础费）、`included_quantity`（整月套餐额度）、
`overage_unit_price`（超量单价）。

创建时校验：名称非空、基础费/额度/超量单价均不得为负，否则分别以
`missing_field` / `negative_amount` 拒绝。

## 2. 计费周期

- 周期以订阅起始时刻 `anchored_at` 为锚点，按**自然月**对齐：
  第 n 期为 `[anchored_at + n 月, anchored_at + n+1 月)`。
- 锚点日在目标月不存在时（如 3/31 遇到 2 月），落到目标月最后一天的同一时刻。
- 周期边界为左闭右开：`2026-02-01 09:00:00` 的用量属于第 1 期，不属于第 0 期。
- **跨周期严格隔离**：用量只写入其发生时刻所属周期的桶，绝不串账。

## 3. 用量上报与窗口聚合

- 用量按 `occurred_at` 用二分插入到周期桶的正确位置，
  **乱序到达**最终也能得到按时间有序、可重复聚合的结果。
- **重复投递**：相同 `event_id` + 相同语义载荷 → 判定 `duplicate`，
  返回首次结果，不重复累计。
- **不同事件**即使数量、时间相同，也视为两次独立使用，正常相加
  （幂等去重的边界是事件，不是业务字段）。

拒绝原因（错误码可区分，见下表）：

| 错误码 | 触发条件 |
| --- | --- |
| `missing_field` | 缺 subscription_id / metric / quantity / occurred_at 等关键字段 |
| `negative_quantity` | 用量额度为负 |
| `usage_before_subscription` | 用量时间早于订阅起始 |
| `usage_after_cancellation` | 用量时间晚于取消时刻（取消时刻当刻仍接受） |
| `subscription_not_found` / `subscription_inactive` | 订阅不存在 / 已取消 |

被拒绝的事件同样登记台账，重放时稳定返回同一拒绝原因，且不改变任何账目。

## 4. 出账（Invoice）

一个订阅一个周期只有一张账单（账单 id 由 `subscription_id + period_index`
确定性派生），账单行分四类：

| 行类型 | 含义 | 符号 |
| --- | --- | --- |
| `base` | 账期起始套餐的整月基础费 | 正 |
| `prorated_credit` | 套餐变更/取消时，当前套餐未使用天数的按比例抵扣 | **负** |
| `prorated_charge` | 套餐变更后，新套餐从变更边界到周期末的按比例费用 | 正 |
| `overage` | 各套餐片段内，实际用量超出**按比例额度**的部分 | 正 |

按比例天数 = `区间整天数 / 周期整天数`（按 24 小时计）。

这套“整月基础费 + 边界抵扣/补差”的写法在代数上**恒等于**把账期按套餐切成
连续片段逐段按日计费，因此：

- 多行之和稳定、无重复计费；
- 抵扣作为独立负向行存在，账目可解释；
- 纯函数计算：相同输入逐行金额、总额、内容校验和（SHA-256）完全一致。

**超量**：片段额度 = 套餐整月额度 × 片段天数/周期天数；片段内用量超出部分
按该套餐超量单价计费。

**中途取消**：末段截断到 `cancelled_at`，仅对当前套餐未使用天数生成一笔
`prorated_credit`，不产生额外补差。

**已结算账单不可重新生成**（`invoice_already_settled`）；草稿账单允许重算覆盖。

## 5. 结算（Settlement）与模拟支付

账单状态机：`draft → settled`（成功）或 `draft → failed`（渠道拒绝，可重试）。

- 模拟网关 `PaymentGateway` 以**账单 id 作为幂等键**：
  - 已成功的键重放返回原交易号，**绝不二次扣款**；
  - 首次失败不缓存失败结果，同键/新结算事件可重试；
  - 零元账单直接成功，不生成交易号。
- 同一账单用新事件再次结算：`invoice_already_settled`。
- 结算事件重放：`duplicate`，交易号不变，成功扣款数不增加。

## 6. 幂等与冲突边界（事件台账）

每个命令必须携带 `event_id`。处理在全局锁内串行完成：

1. 计算 `事件类型 + 规范化载荷` 的 SHA-256 指纹；
2. 台账判定：
   - 未见该 `event_id` → 首次处理（`applied`）；
   - `event_id` 命中、类型与指纹一致 → `duplicate`，回放首次结果
     （首次被拒绝则抛出相同业务错误）；
   - `event_id` 命中但**类型不同或载荷指纹不同** → `event_processed_conflict`，
     明确拒绝，**后来的内容不会覆盖**首次结论。
3. 业务在已提交快照的**深拷贝工作副本**上执行；
4. 成功/业务拒绝都登记台账，并通过存储层**原子保存**一次性提交。

> 说明：`decline_once`（模拟渠道首次失败）是执行选项而非事件语义，
> 不纳入载荷指纹。

**处理到一半中断**：业务修改只发生在工作副本上，`save` 失败则提交快照不变。
- 落盘前崩溃：台账无事件、状态无残留，同事件重试表现为首次应用；
- 网关已扣款但本地落盘崩溃：重试时网关以幂等键返回原交易（不重复扣款），
  本地补记为 `settled`，最终与只成功处理一次完全一致。

**存储原子性**：JSON 存储写临时文件后 `fsync + os.replace`，
外部永远只能看到完整的旧快照或新快照，不会读到半截文件。

## 7. API 一览（前缀 `/api/v1`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/plans` | 创建套餐（event_id 幂等） |
| GET  | `/plans/{id}` | 查询套餐 |
| POST | `/subscriptions` | 创建订阅（起始时刻=服务当前时间） |
| GET  | `/subscriptions/{id}` | 查询订阅（含套餐变更历史） |
| POST | `/subscriptions/{id}/change-plan` | 套餐变更（可指定生效时刻） |
| POST | `/subscriptions/{id}/cancel` | 中途取消 |
| POST | `/usage` | 上报用量 |
| GET  | `/subscriptions/{id}/usage/{period}` | 查询某周期聚合用量（含有序明细） |
| POST | `/invoices` | 生成某周期账单 |
| GET  | `/subscriptions/{id}/invoices/{period}` | 查询账单 |
| POST | `/settlements` | 结算账单（`decline_once` 可模拟首次失败） |
| POST | `/replay` | 重放自检：校验账单指纹与台账一致性 |

业务错误统一返回 HTTP 422：`{"error": <错误码>, "message": ..., "details": {...}}`。

## 8. 如何验证

```bash
uv run pytest                      # 全量单测/并发/重放
uv run pytest -s --log-cli-level=INFO   # 同时查看事件、账期、判定依据日志
uv run python main.py              # 本地启动（默认 http://127.0.0.1:8000）
```

测试覆盖（共 40+ 用例）：

- `test_periods_metering.py`：周期边界、月末锚点、乱序聚合、跨周期隔离、
  各类拒绝原因；
- `test_billing.py`：超量、套餐变更抵扣/补差、中途取消、确定性与校验和；
- `test_settlement.py`：重复结算、失败重试不重复扣款、零元账单、幂等网关；
- `test_idempotency.py`：重复投递、载荷冲突、事件类型冲突、拒绝重放、
  JSON 重启重放；
- `test_concurrency.py`：16/32 线程并发重复用量、并发结算只扣一次、
  冲突事件只有一个生效；
- `test_recovery.py`：落盘瞬间崩溃后无残留重试、已扣款崩溃后补记不重复扣款、
  JSON 不产生半截文件；
- `test_lifecycle_integration.py`：变更 + 取消 + 跨周期 + 两期出账结算 +
  重放闭环；
- `test_api.py`：HTTP 状态码、错误码、幂等 outcome。

日志（logger 名 `metering`）会打印：`event_id`、事件类型、账期
`sub=... period=n [start,end)`、窗口累计、账单行数/总额/校验和、
结算交易号以及 applied / duplicate / rejected / conflict 的**判定依据**。
